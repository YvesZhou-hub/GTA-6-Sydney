# 运行性能：实测范围与剩余瓶颈

## 启动加载第二轮：17 秒降到约 13 秒，加载界面持续响应

同一台 Apple M4、Godot 4.7.2 Forward+ / Metal，源码直接启动游戏（与 `--visual-qa` 同一路径）。`CITY_STARTUP_MS` 两次连续运行为 17,262 / 17,386 ms → 12,605 / 12,699 ms；`--visual-qa` 前后各一次为 17,095 → 13,157 ms。

| 阶段（原生窗口，ms） | 改前 | 改后 |
| --- | ---: | ---: |
| 世界构建 `complete_ms` | 15,232 | 10,612–10,723 |
| 其中：区块合并与收尾 | 约 4,800 | 约 850 |

**区块合并（`harbor_world._rebuild_visual_cell`）。** 以前每个索引都经过四次 `SurfaceTool` 调用展开成独立顶点。现在按材质直接追加整段数组：顶点和法线用 `Transform3D * PackedVector3Array` 整体变换，UV 整段追加，只有索引偏移还是逐项循环；输出改为带索引网格。城市底层网格从 928 万个展开顶点降到 773 万个顶点（索引仍为 928 万），上传的顶点数少约 17%。运行中流式加载近景立面、建筑受损重建也走同一路径，同样受益。

**去掉 GPU 读回。** 改完合并后，剩下的 2.3 秒几乎全部是从 Metal 读回约 6,000 个地标网格（`surface_get_arrays`，每个 0.3–0.4 ms）。新增 `scripts/cpu_mesh.gd`：地标模块改用 `CpuMesh.commit(surface)`，在上传的同时保留 `SurfaceTool` 已经算好的 CPU 数组；普通 `BoxMesh` 按单位立方体缩放得到。合并城市网格和生成结构碰撞体时优先使用这些数组，城市合并完成后释放未用到的副本。近景立面的数组在启动时一并存入缓存，运行中不再读回。

`Mesh.create_trimesh_shape()` 通过 `TriangleMesh` 焊接顶点，会把位置对齐到 0.1 mm。CPU 路径做同样的对齐，200 组随机网格（含城市尺度坐标、带索引与不带索引）的碰撞面与原方法逐位一致，所有“碰撞面与渲染面完全相同”的地标测试照常通过。

**加载界面。** 城市在主线程上构建，以前 12–17 秒内窗口既不重绘也不处理系统事件，macOS 会出现转圈光标，Windows 会标记“未响应”。现在构建各阶段通过 `scripts/loading_progress.gd` 汇报进度：每 60 ms 至多处理一次窗口事件并重绘，加载页显示进度条和当前阶段（铺设街道、搭建海港大桥、生成城市建筑……）。进度条直接向 RenderingServer 提交绘制命令，因为普通控件的重绘要等下一帧，而加载期间没有下一帧。实测两次重绘之间最长 1.4 秒（歌剧院），其余阶段不超过 1.2 秒。加载中关闭窗口会直接退出，此时还没有需要保存的世界。

验证：

- `source/cell_batch_equivalence_test.gd` 保留旧的合并代码，对带索引与无索引、旋转、均匀与非均匀缩放、缺 UV 的输入逐角比较，位置与 UV 完全一致，法线误差约 1e-7；
- 36 个城市、地标与世界测试中，34 个通过；`world_road_probe`（退出码 8）与无头模式下的 `bridge_drive_test` 在未改动的代码上结果相同；
- `--visual-qa` 前后 14 个机位逐像素比较：地铁站、乔治街、北岸引桥、大桥路面等无水面机位无差异，差异只出现在随时间变化的水面反光和岸线浪花上，建筑几何一致；
- `--campaign-qa` 与 `--hud-qa` 通过。

仍未处理：街道约 2.3 秒、普通楼约 2.5 秒、歌剧院约 1.4 秒，均为 GDScript CPU 计算；构建仍在主线程，只是不再让窗口失去响应。

## 启动加载：73.6 秒降到 17.1 秒

同一台 Apple M4、Godot 4.7.2 Forward+ / Metal 源码运行 `--visual-qa`，完整城市的 `CITY_STARTUP_MS` 从 **73,563 ms 降到 17,132 ms**。无界面运行时同一套地标只要约 1.5 秒，差距来自原生渲染器。

原因是地标细节里的方块、横梁和圆环（`city_landmarks.gd` 的 `_append_box` / `_append_beam`）每个都新建一个 `BoxMesh`，再经 `create_from → commit → append_from` 合并：每个方块两次 Metal 上传、两次阻塞式读回。全城有数万个这样的方块，ICC、Tower One、Circular Quay、银行楼和悉尼塔各耗 8–14 秒。歌剧院的梁、叶片与台阶，QVB 的方块与圆柱也有同样写法。

现在只读回一次单位立方体，每个方块在 CPU 上按尺寸缩放和变换；BoxMesh 的顶点随尺寸线性缩放，法线与 UV 不随尺寸变化，所以结果逐顶点一致。QVB 相同参数的圆柱共用一份 CPU 数组。切线不再写入：没有世界材质使用法线贴图，区块合并也只保留位置、法线和 UV。

| 分段（原生窗口，ms） | 改前 | 改后 |
| --- | ---: | ---: |
| ICC | 13,697 | 182 |
| city_landmarks | 10,896 | 259 |
| quay_landmarks | 9,342 | 105 |
| bank_landmarks | 8,371 | 159 |
| sydney_tower_landmark | 8,322 | 104 |
| QVB | 3,800 | 467 |
| 歌剧院 | 3,205 | 1,578 |

验证：`source/box_geometry_equivalence_test.gd` 逐顶点比较新旧路径（位置、法线、UV 最大误差均为 0）；22 个地标与几何测试全部通过。改前改后各截取 14 个地标机位逐像素比较，超过 24/255 的差异只出现在随时间变化的水面波纹上，建筑几何无差异。`icc_landmark_test.gd` 原先假定吊舱网格一定带索引，遇到无索引网格会中途停止并漏掉 5 项检查；现已兼容，完整 50 项通过。

仍未处理的启动开销：区块网格合并约 10 秒、普通楼构建约 8 秒，两者都是 GDScript CPU 计算。

本轮降低了重复新增载具时的模型构建开销，并把世界占用几何缓存的首次构建移到启动阶段。原生 QA 中，两次新增坦克的内部总耗时从 1,894.688 / 794.029 ms 降到 82.618 / 22.699 ms。启动和近距离立面上传仍有明显开销，不能据此承诺稳定帧率或所有场景无卡顿。

## 模板缓存保留了什么

`vehicle_factory.gd` 原来的冷构建路径逐个生成程序网格，再对每个源 surface 执行 `SurfaceTool.create_from → index → commit → append_from`，最后按材质合并。重复新增同类型载具也重复这套提取、临时网格提交和合并工作。新阶段计时区分了这些操作，但没有 GPU 时间戳，不能把整个模型阶段都称作 GPU 读回耗时。

现在首次构建仍执行完整流程，随后按 kind 保存模型模板。后续副本共享不可变 Mesh 几何，每辆车重新创建节点并复制自己的材质、Shape3D、可变 metadata；轮子、炮塔、炮管、枪口和其他运动节点映射到各自的新实例。同车内部原有的材质共享关系保留，跨车辆的喷漆、损伤变色、碰撞形状及炮塔状态独立。模板不保存或克隆 RigidBody 的 ID、位置、生命、燃料、驾驶状态及运行时烟雾等状态。

改进后两次请求的 factory 记录均为 `cache_hit=true`，源网格提取、临时提交和重新合并计数均为零。`source/vehicle_factory_cache_test.gd` 的 131 项 headless 检查覆盖几何/法线/UV/索引、碰撞形状与局部变换一致性，节点名称、运动节点独立性、喷漆隔离、首辆受损后缓存仍干净，以及首辆释放后副本仍可用。该检查验证状态与结构，不替代原生外观或性能验收。

模板数量按车型增长，用户副本数量没有因此设定硬上限；每辆新副本仍需要节点、材质、碰撞和物理资源，庞大车队仍可能增加开销。后续模型代码不得原地修改共享 Mesh，不能为了命中缓存而复用可变运行状态。

世界占用几何通过启动时调用 `MapMigration._geometry(world)` 预热，避免玩家首次请求时支付原来的约 1,078 ms。它把工作移到加载期间，并未消除工作量。安全搜索仍执行完整净空规则，改进后首次搜索仍花费 62.990 ms，未通过跳过碰撞检查换取速度。

## 近距离立面的 64 单元上限

`facade_stream.gd` 只流入附近的立面细节，单元边长 160 m，驻留上限 64。主体建筑、基础碰撞和破坏/存档 ID 仍驻留；这不是整座城市的完整分块卸载。CPU 细节数组由工作线程生成，主线程再合并和提交当前单元网格；移出范围时释放该单元的细节网格。

原生 daylight 报告中的实际读数如下：

| 到达的捕获视角 | 驻留单元 / 上限 | 最近 worker ms | 最近 upload ms | 截至此时累计最大 upload ms |
| --- | ---: | ---: | ---: | ---: |
| 海港 | 7 / 64 | 8.849 | 6.632 | 13.141 |
| George Street 夜景 | 35 / 64 | 0.846 | 0.726 | 121.119 |
| ICC 公共前厅夜景 | 38 / 64 | 34.308 | 29.304 | 156.301 |

`upload_ms` 是主线程 `_commit_ready` 中挂载数组、重建单元网格和清理的墙钟时间，不是独立 GPU 计时。最大值是此前已提交单元的累计峰值，不能归到截图所见的某一栋建筑。156.301 ms 尖峰表明目前仍可能出现可感知停顿；单个大单元的提交尚未按帧时间预算进一步拆分。64 的数量上限约束驻留单元，不保证上传帧时间。

证据：`reports/daylight-native-source.log` 与当次 `user://daylight-qa/report.json`，44/44 通过，报告 SHA256 `586bc66c5988edd3384a2073e28ad315d6cdb1a11c186d3cc07edaaa2b21920c`。这些捕获等待了当前视角加载完成，不是持续驾驶帧率测试。

启动仍需约一分钟以上：`CITY_STARTUP_MS` 在 diagnostics-v2 为 65,637 ms，在 combat-v5 为 75,007 ms，在 daylight 为 84,338 ms。它记录该次源码运行的世界准备计时，不是操作系统启动程序到交互的完整测量；“约 74 秒”只能表达量级，不能替代上述不同运行的实测值。后续仍需削减初始全城构建和主线程大单元提交。

## 运行时渲染路径审计与约束

本次只读检查覆盖昼夜、诊断调节、材质角色、载具动画、战斗特效和世界损伤路径。未发现普通每帧循环反复创建 Shader 代码或切换材质透明/阴影功能的路径。具体已存在的动态行为如下；新加入的夜间局部照明应另行验收，不能继承本次未开火的生成样本结论。

| 路径 | 实际更新 | 当前证据与限制 |
| --- | --- | --- |
| `city_clock → daylight_environment.apply_cycle` | 正常每 0.1 秒更新环境数值、太阳方向/颜色/能量；不切换太阳 visible | 数值变化仍有实际渲染成本，未将其测为编译根因 |
| 天空 | Sky uniforms 最多每 500 ms 更新一次，明确跳时可强制更新；采用 incremental radiance 更新 | 辐照贴图过滤可能有成本；不是更换 Shader 代码 |
| F3、`material_roles.set_role` | 调曝光、雾密度、辉光、粗糙度、金属度与能量等数值 | 不在调节时切透明、SSAO、SSR 或阴影功能开关 |
| `main.apply_settings` | 启动/载入/设置事件重应用质量与阴影功能 | 不是每帧循环；仍应把结构功能切换限制在明确设置操作 |
| `vehicle_weapons → combat_effects.tick` | 12 个预建无阴影 OmniLight；活动爆炸每 tick 写 `visible = age < 0.17` 并衰减能量 | 每次闪光开始/结束确实改变可见性；并未证明其无管线或绘制成本，需要单独事件采样 |
| 载具与爆炸外观 | 轮子/炮塔变换、驾驶员/尾流可见性、已设透明材质的数值淡出 | 网格可见性及透明度数值不是逐帧切换 Material 透明模式 |
| `harbor_world.damage_at` | 命中时更换损伤材质或重建受损单元 | 由破坏事件触发；首次破坏需与普通行驶、单纯生成分开测量 |

Godot 的天空 radiance 更新可能昂贵，incremental 模式将过滤分摊到多帧；调节天空 uniform 仍可能触发这项工作。[Godot Sky 文档](https://docs.godotengine.org/en/stable/classes/class_sky.html)

后续灯光应优先固定预建实例及位置，按时间调整能量，避免逐帧创建/释放灯和切换阴影功能。移动灯或改变可见集合的实际影响要通过原生事件前后的管线计数和帧时间记录判断；固定灯池也不自动保证零开销。应分别采样首次/重复生成、首次开火/破坏、时间切换及快速跨单元移动，保留模型、占用缓存、位置搜索、worker、主线程提交和管线计数，避免只看 FPS 就归因。

最终源码回归在 `reports/v017-source/combat-source-witnesses.json`：九组共 412 项通过，逐项运行前后 168 个游戏源码/资源文件及对应测试哈希保持一致。该证据用于确认缓存、载具物理、状态、战斗、召唤与诊断的兼容性；不把 headless 的用时或通过数量换算成原生性能承诺。
