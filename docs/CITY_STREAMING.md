# 城市近景立面加载

当前实现只按距离生成、上传和释放**近景立面细节**。普通 OSM 建筑的基础外壳、CPU 基础几何、独立碰撞体和损坏 ID 在城市初始化时完整建立，随后仍全量常驻。道路、地形、地标、公共室内和其他游戏实体没有因此变成分区加载；这不是整个悉尼世界的流式加载系统。

实现位于 `game/scripts/facade_stream.gd`，由 `HarborWorld` 持有。`main.gd` 在建城前设置 `stream_details=true`，运行时传入当前相机位置与人物/载具速度。未开启该元数据的独立建筑夹具沿用立即生成全部立面细节的路径。

## 实际范围与预算

| 参数 | 当前行为 |
|---|---|
| 空间网格 | 160 × 160 m，使用结构中心分配到单个格子 |
| 规划间隔 | 每 0.15 秒重新选取目标格子 |
| 加载距离 | 格子中心距相机位置或前方预测点小于 560 m |
| 前方预测 | XZ 速度向量限制长度为 560，再乘 0.65；最大前移 364 m |
| 保留距离 | 不再需要的格子通常保留到距相机中心超过 780 m；满缓存时可提前驱逐 |
| 硬上限 | 最多 64 个 resident 细节格子，提交新格子前预留位置 |
| 高空 | 相机 Y ≥ 900 m 时清空近景目标并驱逐细节；基础外壳与碰撞继续存在 |
| 工作线程 | 同时最多一个 `WorkerThreadPool` 任务，一个任务处理一个格子 |
| 主线程提交 | 每次 tick 最多提交一个已完成格子，然后可派发下一格子 |
| 细节绘制距离 | 合并细节 MeshInstance 的 `visibility_range_end=320`、margin=60；细节不投射阴影 |

560/780 m 是到**格子中心**的距离，不是逐栋建筑到相机的精确距离。64 是格子数预算，不是 64 MB、64 个三角面，也不是固定帧耗时保证；一个格子可能包含多栋建筑和多个材质表面。空细节格子也占 resident 条目，以免持续重新尝试。一个尚未提交的任务及其临时 CPU 数组不计入这 64 个已驻留格子。

目前没有按毫秒拆分单个密集格子的生成或上传。主线程需要一次完成该格子的合并与上传，因此不能从“一次一个格子”推出“没有卡顿”。实际上传耗时必须在完整原生 App 中测量。

## 从源轮廓到可见细节

1. `City.build_buildings` 始终生成每个普通建筑分组的基础外壳、碰撞和稳定 `osm/.../storey_group/...` ID。开启加载后，仅为符合条件的立面记录 `deferred_facade` 描述，不立即执行近景网格生成。
2. `HarborWorld._build_structure_batches` 创建基础与细节两类网格，先合并基础表面。普通建筑的细节数组此时不存在。
3. 规划选取附近最多 64 个目标格子。工作线程只使用源记录和上下标高，通过 `City._facade_relief` 生成 CPU 顶点数组；它不上传 GPU 网格，也不操作场景节点。
4. 主线程确认任务已完成，并检查该格子仍在目标列表中。快速跳转后不再需要的旧结果会丢弃；满缓存时先驱逐一个非目标格子，没有可用位置则拒绝提交。
5. 主线程将临时数组交给原有材质分组与空间合并路径。上传完成后删除结构描述中的临时近景数组，保留源描述供返回时重建。
6. 驱逐将细节节点的 `mesh` 置空，基础网格、碰撞和结构记录保持原来的资源与身份。世界退出时，`close()` 等待在途任务结束，清空临时输出并释放工作线程持有的世界引用。

普通立面细节沿现有 OSM 边界生成楼层线脚和窗框，属于已有程序化建筑表达。加载系统不新增随机建筑、改变坐标或改写现实高度来源。带有 `near_facade` 标记的既有网格也参与细节显示层，但其原始 Mesh/缓存可能已经在建城时创建；不能把所有近景对象的 CPU 内存都算作已经释放。

源数据中的 `way/556844015` 高度为 15 m，但其每条小轮廓边均不足 1.2 m，细节生成器会返回空数组。工作线程和提交路径均有空数组守卫。这个格子可以完成加载、保持基础建筑存在，并记为 resident，不会因为没有细节而每帧重复生成。

## 损坏、存档与夜窗身份

破坏状态继续由 `HarborWorld.destroyed` 和 `partial_damage` 管理，不存放在细节缓存中。损坏会让相应细节格子失效；下次重新生成时跳过已毁结构，合并时也再次检查销毁状态，并为达到现有擦伤阈值的表面使用损坏材质。卸载和返回不会清除这些字典，不能使建筑或碰撞复活。加载本身不创建新的损坏 ID 或存档格式。

普通建筑基础表面的 UV2 携带固定建筑 ID 种子和用途代码。批处理逐顶点保留 UV2，使多个共用材质的建筑仍有各自稳定的夜窗身份。近景框架生成/驱逐不重排基础表面上的窗口种子。夜窗与材质调参的具体范围见 [材质角色说明](MATERIAL_ROLES.md)。

## 诊断与验证

`world.streaming_stats()` 返回实际 `near_facade_only` 状态，包括 `cell_size_m`、`resident`、`limit`、`resident_cells`、`wanted`、`pending_worker`、`builds`、`evictions`、`last_worker_ms`、`last_upload_ms`、`max_upload_ms` 和 `base_collision_resident`。这些是本次运行的状态与耗时；`max_upload_ms` 只代表已经提交过的格子，不是全城最坏情况测量。

`source/facade_stream_test.gd` 已通过 **27 项 headless 检查**。夹具使用真实 `HarborWorld` 的轻量子类，仅跳过 `_ready()` 的全城构建，再调用生产 `City.build_buildings`、空间批处理、`WorkerThreadPool` 和真实物理射线。第一组含 3 个测试棱柱及上述 1 个真实地图记录；第二组含 66 个测试格子，用于确定性的容量边界验证。容量压力测试有意控制调度内部状态，以覆盖正常距离规划不一定立即触发的满缓存提交情形。

检查覆盖：初始近景不生成、附近加载与远处卸载、基础网格/碰撞资源/ID 不变、UV2 保留、空结果不循环、损坏建筑返回后不复活、快速跳转丢弃旧结果、高空卸载、带在途任务关闭，以及实际 64 个细节网格的硬上限和没有空位时拒绝额外提交。

```sh
tools/runtime/godot --headless --path game --script ../source/facade_stream_test.gd
```

本地证据为 `reports/facade-stream/checks.json`、`headless.log` 和 `freeze.json`，绑定测试及 `facade_stream.gd`、`city_map.gd`、`harbor_world.gd` 的 SHA-256。当前报告 27/27 通过，无运行时 ERROR/WARNING。后续修改这些文件应重新生成证据。

该夹具未运行完整城市或 GPU，不能证明原生帧率、内存节省、快速飞行时的细节出现速度或视觉过渡质量。全城原生 App 的性能采样与逐图验收应单独报告，不把这 27 项计入导出 App 的原生检查总数，也不把当前范围描述为“全城按需加载”。
